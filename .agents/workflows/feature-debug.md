# feature-debug

系统化缺陷定位与修复流程。Agent 在收到"调试 bug"、"定位报错"、"排查异常"、"修复回归"、"测试失败"等请求时，必须先加载本工作流。

---

## 步骤

### 1. 复现
- 获取完整的错误信息和堆栈跟踪
- 构造最小可复现用例
- 确认问题在最新代码上存在（`git status` 确认无未提交修改干扰）

### 2. 定位根因
- 从堆栈跟踪向下追踪到项目源码（跳过 `node_modules/`）
- 使用 `grep` 搜索相关符号、函数、类型
- 阅读相关源文件，理解数据流和控制流
- 基于证据下结论，不靠猜测
- 如涉及多个可能原因，逐一排除

### 3. 最小修复
- 只改导致问题的代码，不改无关代码
- 不在此步骤中重构或优化
- 修复根因而非症状（如 null check 掩盖了不应为 null 的逻辑错误）
- 如涉及类型问题，修复类型定义而非添加类型断言

### 4. 回归测试
- 将复现用例转化为测试，加入对应测试文件
- 确认修复后该测试通过
- 确认所有现有测试仍然通过

### 5. 验证
- `npx tsc --noEmit` 0 错误
- `npx vitest run` 全部通过

### 6. 记录
- 如问题对应 `.agents/todo/` 中某个 todo，更新其状态为 done
- commit message 使用 `fix:` 前缀，描述根因和修复

---

## 原则

| 原则 | 说明 |
|------|------|
| 治本不治标 | 修复根因，不是加 try-catch 掩盖 |
| 改动最小化 | 只改必要的行，不顺手重构 |
| 必有回归测试 | 每个修复都有对应的测试用例 |
| 修复后必验证 | typecheck + test run 全部通过 |
| 证据驱动 | 基于日志和堆栈定位，不猜测 |
