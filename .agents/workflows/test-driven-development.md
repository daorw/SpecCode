# Workflow: Test-Driven Development

## Description

通用的 Red-Green-Refactor 工作流。适用于功能开发、bug 修复、重构和行为变更。

## When to Use

- 新增功能
- Bug 修复
- 行为变更的重构
- 任何需要验证正确性的代码变更

## Exceptions

在以下情况下可跳过 TDD（需用户确认）：
- 生成代码
- 纯配置变更
- 纯文档变更
- 原型验证

## Steps

### 1. RED — 编写失败的测试

- [ ] 选择最小可观察行为进行规格说明
- [ ] 在编写生产代码前添加或更新测试
- [ ] 优先测试真实行为而非实现细节
- [ ] 根据被测单元选择合适的测试层级（单元/集成/E2E）
- [ ] 仅在需求本身是不变量时使用 Property-Based 测试

#### 测试策略选择

| 测试类型 | 适用场景 |
|----------|----------|
| 单元测试 | 纯函数、工具函数、数据转换 |
| 集成测试 | API 路由、数据库交互、外部服务调用 |
| E2E 测试 | 关键用户路径、端到端流程 |

### 2. Verify RED

- [ ] 运行最窄范围的测试命令
- [ ] 确认测试因预期原因失败
- [ ] 如果测试立即通过或因配置问题失败，修复测试本身

### 3. GREEN — 实现最小通过代码

- [ ] 仅修改使失败测试通过所需的生产代码
- [ ] 保持现有架构边界
- [ ] 避免不相关的重构或投机性修改

### 4. Verify GREEN

- [ ] 重新运行目标测试，确认通过
- [ ] 当变更跨越模块边界时，运行相关模块测试

### 5. REFACTOR

- [ ] 测试通过后，清理命名、重复代码和结构
- [ ] 每次有意义的清理后重新运行测试

### 6. 扩展验证

- [ ] 添加下一个失败测试，重复循环
- [ ] 运行完整测试套件确认无回归
- [ ] 对并发敏感的变更运行竞态检测
- [ ] 受影响的集成路径需通过集成测试验证

## Commands

```bash
# 运行单个测试文件
# <test-command> <test-file>

# 运行单个测试用例
# <test-command> -t "<test-name>"

# 运行完整测试套件
# <test-suite-command>

# 类型检查（如适用）
# <typecheck-command>
```

## Output expectations

- 最终变更包含驱动它的失败优先测试
- 目标测试和完整套件均通过
- 受影响的集成路径已覆盖或明确说明未运行原因
- 最终响应中列出执行的验证命令
