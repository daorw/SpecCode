# 开发指南

## 最小路径原则实践

### 什么是最小路径原则
选择最简单、最直接的方式实现功能，避免过度设计。

### 实践要点
1. **先实现，再优化**：先让功能跑通，再考虑优化
2. **避免过早抽象**：除非有明确复用需求，否则不抽象
3. **减少配置**：能用代码表达的不做配置
4. **减少依赖**：优先使用标准库，谨慎引入第三方依赖

### 决策流程
```
需求 -> 最简单的实现方式是什么？
      -> 能否复用现有代码？
      -> 实现后是否满足需求？
      -> 是否有性能问题需要优化？
      -> 完成
```

## 第一性原理思考

### 核心问题
这个功能/问题的本质是什么？

### 思考步骤
1. 剥离现有方案，回到问题本身
2. 识别最基本的要素
3. 从这些要素出发构建解决方案
4. 对比现有方案，选择最优路径

### 示例
- 不是"我要加一个 Redux"，而是"我需要状态管理吗？需要什么样的状态管理？"
- 不是"我要建一个微服务"，而是"这个功能需要独立部署吗？"

## 测试编写指南

### 测试原则
1. **测试行为，而非实现**：测试应该验证功能是否工作，而不是实现细节
2. **一个测试一个断言**：保持测试聚焦
3. **测试命名清晰**：描述预期的行为
4. **避免测试代码影响实现**：不要为了让测试通过而扭曲实现

### 测试结构
```python
# 示例：Python 测试
def test_feature_does_something():
    # Arrange - 准备数据
    input_data = create_test_data()
    
    # Act - 执行操作
    result = feature.process(input_data)
    
    # Assert - 验证结果
    assert result.expected_property == expected_value
```

### 测试覆盖
- 正常路径
- 边界条件
- 错误情况
- 集成点

## 影响评估检查清单

在修改代码前，评估对以下方面的影响：

### 功能影响
- [ ] 现有 API 是否保持兼容？
- [ ] 用户界面是否有变化？
- [ ] 数据格式/存储是否有变化？
- [ ] 配置方式是否有变化？

### 性能影响
- [ ] 响应时间是否有影响？
- [ ] 资源消耗是否有变化？
- [ ] 并发处理能力是否有影响？

### 依赖影响
- [ ] 是否新增依赖？
- [ ] 是否改变依赖版本要求？
- [ ] 是否影响构建/部署流程？

## 常见问题处理

### 与现有代码风格冲突
**方案**：遵循现有风格，即使个人偏好不同。一致性比个人偏好更重要。

### 测试难以编写
**方案**：可能是设计问题，考虑简化实现或分离关注点。

### 功能边界不清晰
**方案**：与最小路径原则冲突时，优先明确需求边界，避免过度扩展。

### 规范不明确
**方案**：参考项目现有代码，选择最常见的模式。如有疑问，记录下来待 AGENTS.md 更新时补充。
